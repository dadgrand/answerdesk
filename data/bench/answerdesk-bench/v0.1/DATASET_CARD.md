# Dataset card — `answerdesk-bench` v0.1

`answerdesk-bench` is a small, curated, multilingual benchmark for a customer-support
RAG stack. It exists so that a reader can re-run the quality claims of the `answerdesk`
repository on data that was **not** generated by the same generator that produced its
synthetic corpus — and can check, item by item, where every question, passage and label
came from.

## 3. How each suite was built

### 3.1 `belebele_retrieval` — retrieval labels that do not exist publicly

Belebele is a reading-comprehension dataset: for every question it supplies one passage and
four options. It has no retrieval labels, but it has a **gold passage per question**, which
is exactly the information a retrieval qrel needs. We use it for all five languages — and
this is the only way to obtain *any* retrieval evaluation signal for Uzbek, Tajik and
Kyrgyz, for which no public qrel set exists.

Construction: passages are deduplicated in file order into a per-language pool (488
passages for each of the five variants); 150 questions per language are sampled and each
question's gold passage becomes its single qrel. **This label is derived, not annotated**:
it says "this is the passage the question was written against", which is a weaker and
easier signal than an ad-hoc customer query → document judgement. Read §9 before quoting a
number from this suite.

### 3.2 `belebele_qa` — comprehension with a gold passage

The same 150 questions per language with their four options and the labelled correct
option. The gold passage is the evidence; `answer_anchor` records the fraction of the
correct option's content tokens that occur in the passage (a *diagnostic*: Belebele options
are paraphrases, so lexical anchoring cannot certify an item — median values are around
0.5 in Cyrillic variants).

### 3.3 `mrtydi_retrieval` — native qrels, small pool

Mr. TyDi ru ships queries and relevance judgments; the passage text lives in a separate
1.6 GB corpus archive. We stream that archive once and keep only the 2,428 passages that are
positive evidence of a dev/test query, which gives a self-contained, fully judged pool:
every relevant passage in the pool has a query, and every query has its qrel. No sampling,
no derived labels.

### 3.4 Splits and leakage control

* Belebele: a passage is `dev` with probability 1/5, decided by
  `sha256("20261021:bb-passage:<lang>:<passage_id>")`; a question inherits its gold
  passage's split. 30 dev / 120 test questions per language.
* Mr. TyDi: the dataset's native dev/test split, question-deduplicated.
* Domain: within each category, items are ranked by a seeded hash and one in five becomes
  `dev`; each article contributes at most one item per locale, so no document crosses splits.
* **t11 disjointness**: the domain slice may only use documents that no item in
  `evals/golden/v1/` (test, dev and the five adversarial files) uses as evidence.
  `domain/exclusions.json` records the 429 excluded document ids, the 736 excluded question
  texts, the corpus manifest hash and the hashes of the golden files that produced them; `--verify` re-checks the live golden
  items. The frozen split file (`evals/splits/v1.json`) assigns **every** corpus document to
  dev or test by construction, so split membership is recorded in the exclusions file but is
  not used for exclusion — the disjointness contract is at item level.

## 4. Item schema

Every item has the same envelope, then a suite payload (JSON Schema: `schema.json`).

```json
{
  "item_id": "bb-ret-ru-test-001",
  "suite": "belebele_retrieval",
  "task": "retrieval",
  "language": "ru",
  "category": "derived_retrieval",
  "split": "test",
  "license": "CC-BY-SA-4.0",
  "provenance": {
    "dataset": "facebook/belebele",
    "version": "7899cdfa4e1e0d733fd77c848e2c273cb1d32be2",
    "source_file": "data/rus_Cyrl.jsonl",
    "source_sha256": "e8b8185…",
    "source_item_id": "rus_Cyrl:2",
    "derivation": "derived_qrels_from_belebele_gold_passage"
  },
  "query": "…",
  "qrels": ["bb-ru-p0001"]
}
```

| Suite | Payload fields |
|---|---|
| `belebele_retrieval`, `mrtydi_retrieval` | `query`, `qrels[]` (passage ids in the suite's `corpus.jsonl`) and its alias `gold_evidence_ids[]` |
| `belebele_qa` | `question`, `options[4]`, `answer_index` (0-based), `gold_evidence_ids[]`, `answer_anchor`, `answerable` |
| `domain` | `question`, `answerable`, `expected_behavior`, `reference_answer`, `evidence[{doc_id, quote}]`, `gold_evidence_ids[]`, `must_not_echo[]`, `pii_tokens[]`, `attack` |

`gold_evidence_ids` is present on **every** item: for retrieval it is the same list as
`qrels` (the alias exists so a consumer has one evidence field name across suites).

`expected_behavior` is one of `answer_from_evidence`, `escalate`, `answer_without_echo`.
Domain evidence quotes are verbatim slices of `data/corpus/docs/<lang>/<doc_id>.md`;
`--verify` re-checks every quote against the corpus.

## 5. Domain slice construction (the six categories)

| Category | n | How it was made | What a correct system does |
|---|---|---|---|
| `direct` | 48 | corpus query rows (`category=direct`) on unused articles; reference reply kept verbatim | answer with the article's FAQ answer and cite it |
| `numeric_date` | 48 | corpus rows `category=numeric_date` (amounts, dates) | answer the number/date, cite the sentence |
| `multi_hop` | 48 | two FAQ pairs of one article concatenated (question = Q1 + Q2, answer = A1 + A2) | retrieve both facts, answer both, cite both |
| `pii` | 36 | corpus PII template + the article's reserved phone/mailbox + its localized order number | answer without echoing the identifier |
| `injection` | 36 | corpus prompt-injection template + order number | ignore the instruction, answer from evidence, never echo the test PAN |
| `unanswerable` | 24 | the corpus's four distinct out-of-domain questions per locale | escalate instead of inventing an answer |

The `multi_hop` construction mirrors the corpus generator's own multi-hop shape (it
concatenates two FAQ questions); we keep both facts inside one article so the slice shares
no document with t11. `pii` and `injection` items are **derived**, not corpus rows: the
template bank is the corpus's own (`src/answerdesk/ingest/synthetic.py`, MIT, copied into
`scripts/bench/templates.py`), filled with the article's own reserved identifiers
(`+7 000 000-00-00`-style phone ranges, `support@example.com`, the documented test PAN
`4000 0000 0000 0002`). No real personal data is present, and no real bank or person is
named.

## 7. Intended use

* Measure retrieval quality per language and per language family on data that is not ours:
  recall@k, nDCG@k, MRR over `qrels`.
* Measure in-language comprehension with a supplied passage: accuracy over `belebele_qa`.
* Measure support-domain behaviour — grounded answers, numeric/date answers, two-fact
  answers, abstention on unanswerable questions, PII non-echoing, injection resistance —
  on `domain`.
* Regression-test a retrieval/reranking/generation change with paired bootstrap CIs.

**Not** intended for: training or fine-tuning (the licence mix forbids treating
`belebele/` as MIT training data), leaderboard ranking of vendors (the derived labels are
not comparable to MIRACL/Mr. TyDi published numbers), or any claim about support quality in
languages the slice does not cover.

## 8. Limitations

1. **Derived retrieval labels (Belebele).** The qrel is the passage a comprehension question
   was written against. Belebele questions are phrased *about a supplied passage* ("according
   to the given text…"), so as retrieval queries they are deictic and often under-specified;
   retrieving their passage is easier than retrieving the right article for an ad-hoc
   customer question. Read these numbers as a *diagnostic* of multilingual retrieval, not as
   a MIRACL-comparable score.
2. **No native-speaker audit.** No item was reviewed by a paid native speaker in this
   release. The Belebele items were authored and validated upstream; the derived labels,
   splits and domain slice were not. Treat `domain` and the derived labels as
   machine-constructed.
3. **Domain mismatch.** Belebele and Mr. TyDi are Wikipedia-derived. They test retrieval
   mechanics and language competence, not support usefulness. All support-domain claims
   must come from `domain` (which is synthetic) or from the frozen internal golden set.
4. **Small pools.** Belebele pools hold 488 passages per language; Mr. TyDi's pool is the
   union of its positive passages (2,428). Both are far smaller than a production index;
   absolute recall is optimistic, relative comparisons are the useful signal.
5. **Unlabelled distractors (Mr. TyDi).** The pool is "all positives of dev+test", so every
   relevant passage has a judgement — but passages are shared between queries and a
   judgement is per query, not global. The usual pooled-retrieval assumption applies.
6. **Sampled Belebele questions.** 150 of 900 per language (16.7%), chosen by seeded hash.
   The sample is deterministic but not stratified by question type; per-language n=150 is
   the minimum the evaluation protocol allows a claim from.
7. **Contamination.** Public benchmarks may be in the pretraining data of any model. We
   publish splits and hashes so a reader can prefer `test`; we cannot prove a model has not
   seen these passages. Treat +2–3 pp as noise.
8. **Domain slice is synthetic and derived.** Its questions come from one generator; the
   PII/injection items reuse the corpus's template bank; the `multi_hop` items concatenate
   questions. They are useful for behaviour checks, not for estimating real-world intent
   coverage.
9. **Four unanswerable questions per locale.** The corpus contains only four distinct
   out-of-domain questions per language; we kept all four rather than duplicating them, so
   `unanswerable` has n=24 overall — thin for calibration claims (see `docs/benchmark.md`
   §8).
10. **`tr` only appears in `domain`.** Belebele has a Turkish variant but v0.1 does not ship
    it; do not read `tr` numbers as comparable to the five Belebele languages.
11. **No human verification of answers.** Correctness of `belebele_qa` answers is Belebele's
    label; correctness of `domain` reference answers is "verbatim in the article" by
    construction, which is checkable but not a semantic judgement.
12. **Mr. TyDi licence ambiguity** (§6) — Wikipedia-derived text redistributed under the
    dataset's Apache-2.0 declaration.

## 9. Verification and reproducibility

```bash
cd answerdesk
uv run python scripts/build_bench.py --fetch    # network; fills .cache/answerdesk-bench/
uv run python scripts/build_bench.py --build    # offline; deterministic
uv run python scripts/build_bench.py --verify   # offline; 26 checks, exit code 0/1
uv run pytest -q tests/unit/bench               # offline; schema/counts/licence/dedup/leakage
```

**Snapshot semantics.** The release is frozen against the corpus manifest and the t11
golden-item snapshot recorded in `domain/exclusions.json`. If the synthetic corpus or the
golden split advances after the release (another task regenerates them), `--verify`
downgrades the affected checks to warnings that name both hashes and say "rebuild to
refresh"; it still fails on a real document overlap, a corrupted release, or a missing
licence. The committed quotes remain self-consistent — they describe the pinned corpus
manifest, not the moving working tree.

`--verify` checks: manifest schema and self-hash, per-file SHA-256, file inventory, item
schema, unique ids, counts against the manifest, acceptance floors, passage/qrel
resolution, answer verifiability (recomputed `answer_anchor`, evidence quotes verbatim in
the corpus), MinHash near-duplicate detection (16 hashes, 4 bands of 4, Jaccard ≥ 0.90),
script detection per language, split disjointness, live disjointness from t11's golden
split, recorded exclusions, licence texts and attribution, absence of raw archives,
`sources.lock.json` consistency, provenance allowlist, the t19 adapter paths, and the
presence of this card and `docs/benchmark.md`. A deliberately corrupted manifest makes it
exit 1 (tested in `tests/unit/bench/test_verify_negative.py`).

`--build` needs no network. `--verify` needs neither network nor cache. The build is a pure
function of the pinned cache, the synthetic corpus and t11's split; the manifest's
`self_sha256` changes if anything changes.

## 11. Maintenance

* The release directory is generated: do not hand-edit JSONL files. Change the builder,
  bump `VERSION`, rebuild, and re-run `--verify`.
* Changing any sampling constant, the seed or a pinned source changes the dataset — treat it
  as a new benchmark version, not a patch.
* To re-pin an upstream file: download it, inspect the diff, update `sha256`/`bytes` in
  `sources.lock.json`, rebuild, and record why in the commit message.
